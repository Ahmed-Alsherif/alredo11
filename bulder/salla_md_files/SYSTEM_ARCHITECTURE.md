# معمارية النظام

## المرجعية

هذه المعمارية مبنية على النظام المنفذ فعلياً مع إضافة الوظائف المخطط لها والتي لم تُنفذ بعد.
كل مكون مرتبط بمتطلبات وظيفية محددة من وثيقة المتطلبات.

## نظرة عامة

يتكون النظام من أربع طبقات رئيسية:

1. تطبيق جوال Expo (React Native) — للمشترك والسائق والمندوب.
2. لوحة إدارة Next.js + TypeScript + Tailwind CSS — للأدمن والمحاسب.
3. Backend باستخدام Django REST Framework.
4. قاعدة بيانات MySQL.

```text
┌─────────────────┐     ┌──────────────────┐
│  Mobile App     │     │  Dashboard       │
│  (Expo + RN)    │     │  (Next.js + TS)  │
│                 │     │                  │
│  • المشترك      │     │  • الأدمن        │
│  • السائق       │     │  • المحاسب       │
│  • المندوب      │     │                  │
└────────┬────────┘     └────────┬─────────┘
         │       HTTP/JWT        │
         └───────────┬───────────┘
                     │
         ┌───────────▼───────────┐
         │   Django REST API     │
         │   (Backend)           │
         │                      │
         │  accounts │ zones    │
         │  subscribers │ tracking│
         │  finance │ complaints│
         │  recycling │ notifications│
         │  reports             │
         └───────────┬──────────┘
                     │
         ┌───────────▼──────────┐
         │   MySQL Database     │
         └─────────────────────┘
```

## فئات المستخدمين

### تطبيق الجوال

- **المشترك (Subscriber)**: التسجيل الذاتي، الاشتراكات، تتبع الشاحنة، الشكاوى، إعادة التدوير.
- **السائق (Driver)**: مسار اليوم، تحديث الموقع، البلاغات الميدانية، تأكيد إعادة التدوير.
- **المندوب (Agent)**: تسجيل المشتركين، التحصيل النقدي، تسليم العهدة، متابعة المتأخرين.

### لوحة الإدارة

- **الأدمن (Admin)**: إدارة كاملة — مناطق، مسارات، موظفين، مشتركين، شكاوى، تقارير.
- **المحاسب (Accountant)**: مطابقة العهد، المصروفات، الجزاءات، السلف، التقارير المالية.

## مبدأ الواجهات حسب الدور

- كل دور له واجهة مستقلة يتم التوجيه إليها تلقائياً بعد تسجيل الدخول بناءً على `user.role`.
- لا توجد شاشة اختيار الدور — التوجيه تلقائي 100%.
- لا يتم بناء نظام صلاحيات تفصيلي — الفصل يتم عبر واجهات مستقلة لكل دور.

## مكونات Backend

### وحدة الحسابات والمصادقة (`accounts`)

النماذج: `User`, `EmployeeProfile`, `DriverProfile`, `AgentProfile`, `AccountantProfile`, `EmployeeDocument`.

المسؤوليات:

- تسجيل الدخول عبر JWT (`/api/auth/login/`).
- التسجيل الذاتي للمشتركين (`/api/users/register/`).
- إدارة المستخدمين والموظفين.
- إدارة وثائق الموظفين الرقمية.
- إعادة تعيين وتغيير كلمات المرور.
- التوجيه التلقائي حسب الدور.

ملاحظات تقنية:

- `User` يرث من `AbstractBaseUser` + `PermissionsMixin` مع custom `UserManager`.
- الموظف يتكون من `User` → `EmployeeProfile` → `DriverProfile/AgentProfile/AccountantProfile` (هيكل وراثة ثلاثي).
- خاصية `user.profile` تعيد البروفايل المناسب تلقائياً حسب الدور.
- خاصية `user.profile_zone` تعيد المنطقة من البروفايل الفرعي.

المتطلبات: STF-01 إلى STF-07.

### وحدة المناطق والمسارات (`zones`)

النماذج: `Zone`, `Route`.

المسؤوليات:

- إدارة المناطق الجغرافية وحدودها (مخزنة كـ JSON coordinates).
- إدارة قوالب المسارات وأيام الجمع.
- ربط السائقين بالمسارات (`Route.driver`).
- ربط المندوبين بالمناطق (`AgentProfile.zone`).
- تجميد المسارات مؤقتاً (`Route.status = frozen`).

ملاحظات تقنية:

- حدود المنطقة (`boundaries`) مخزنة كـ `JSONField` — قائمة إحداثيات `[{lat, lng}, ...]`.
- `Zone` يحتوي على خصائص محسوبة: `subscribers_count`, `drivers_count`, `agents_count`.

المتطلبات: OP-01 إلى OP-14.

### وحدة المشتركين والاشتراكات (`subscribers`)

النماذج: `Subscriber`, `SubscriptionPlan`, `SubscriptionLog`.

المسؤوليات:

- تسجيل وتحديث بيانات المشتركين.
- التقاط الموقع الجغرافي (GPS) عند التسجيل.
- التحقق من نطاق التغطية (GPS fallback: ربط بمنطقة المندوب إذا لم يُلتقط الموقع).
- توليد رقم اشتراك فريد (`SUB-XXXX`) تلقائياً.
- إدارة خطط الاشتراك (باقات ديناميكية من الباكيند).
- التصنيف اللوني التلقائي (`update_color_status`):
  - أخضر: مسدد أو لم ينتهِ اشتراكه.
  - أصفر: متأخر ≤ 30 يوماً.
  - أحمر: متأخر > 30 يوماً أو بدون اشتراك نهائي.
- الإيقاف المؤقت (`pause/resume`) مع تمديد تاريخ الانتهاء تلقائياً.
- الأرشفة (`archive`) مع سبب الأرشفة.
- سجل الاشتراكات (`SubscriptionLog`) لتتبع تاريخ كل تجديد/تغيير باقة.

ملاحظات تقنية:

- `Subscriber.save()` يولّد `subscription_id` تلقائياً إذا كان فارغاً.
- عند تسجيل مشترك جديد، يجب استدعاء `update_color_status()` فوراً ليظهر بالأحمر (مستحق الدفع).
- `SubscriptionLog` يربط بين المشترك والباقة والدفعة مع تواريخ البداية والنهاية.

المتطلبات: SUB-01 إلى SUB-12.

### وحدة التتبع الجغرافي (`tracking`)

النماذج: `TruckLocation`, `CollectionVisit`.

المسؤوليات:

- استقبال تحديثات موقع الشاحنة لحظياً من تطبيق السائق.
- تخزين سجل المواقع مع الطابع الزمني.
- توفير بيانات الخريطة المباشرة للمراقبة.
- إدارة زيارات الجمع اليومية (pending/collected/skipped/issue).
- توفير مواقع المشتركين كـ Pins على خريطة السائق/المندوب.

ملاحظات تقنية:

- `TruckLocation` يربط بالسائق مباشرة (لا يوجد جدول شاحنات مستقل — رقم الشاحنة في `DriverProfile.truck_number`).
- `CollectionVisit` يحتوي على `unique_together = ['route', 'subscriber', 'visit_date']` لمنع التكرار.

المتطلبات: GEO-01 إلى GEO-05.

### وحدة الإشعارات (`notifications`)

النماذج: `Notification`.

المسؤوليات:

- حفظ مركز الإشعارات الداخلي.
- أنواع الإشعارات: `truck`, `payment`, `complaint`, `recycle`, `system`.
- تتبع حالة القراءة (`is_read`).

إشعارات يتم إنشاؤها تلقائياً عند:

- تأكيد دفع المندوب → إشعار إيصال للمشترك (NOT-04).
- بلاغ ميداني من السائق → إشعار للمشترك والإدارة (NOT-02).

إشعارات مخطط لها (لم تُنفذ بعد):

- إشعار موعد الجمع ليلة الموعد (NOT-01).
- تنبيه انتهاء الاشتراك (NOT-03).
- إشعار تجميد المسار (OP-10).

المتطلبات: NOT-01 إلى NOT-05.

### وحدة الشكاوى والجودة (`complaints`)

النماذج: `Complaint`, `FieldReport`, `ServiceRating`.

المسؤوليات:

- استقبال شكاوى المشتركين (نصية + مصورة).
- أنواع الشكاوى: `late`, `damaged`, `missing`, `other`.
- حالات الشكوى: `new`, `in_progress`, `resolved`.
- البلاغات الميدانية المصورة من السائق: `full`, `damaged`, `missing`, `empty`.
- تقييم الخدمة الشهري (1-5) مع تعليق اختياري.

المتطلبات: QC-01 إلى QC-04.

### وحدة إعادة التدوير (`recycling`)

النماذج: `RecycleRequest`, `PointsTransaction`, `Reward`.

المسؤوليات:

- طلبات جمع إعادة التدوير مع نوع الفئة وعدد الأكياس.
- فئات الفرز: `plastic`, `metal`, `paper`, `bread`.
- تأكيد السائق لاستلام الأكياس (`confirmed_by`).
- منح النقاط تلقائياً عند التأكيد.
- لوحة المتصدرين حسب المنطقة.
- مكافآت شهرية تلقائية.

ملاحظات تقنية:

- فئات الفرز مخزنة كـ `TextChoices` في النموذج حالياً — يمكن تحويلها لجدول مستقل (`RecyclingCategory`) لمرونة أكبر.

مخطط لها (لم يُنفذ بعد):

- سجل الأثر البيئي والرتب التلقائية (`EnvironmentalImpactRecord`).
- فئات فرز كجدول مستقل قابل للإدارة من Dashboard.

المتطلبات: REC-01 إلى REC-06.

### وحدة الشؤون المالية (`finance`)

النماذج: `Payment`, `Expense`, `Advance`, `Penalty`, `StaffReward`, `CollectionSettlement`.

المسؤوليات:

- تسجيل التحصيل النقدي الميداني بواسطة المندوب.
- إصدار إيصال رقمي تلقائي (`REC-{pk:06d}`) عند إنشاء الدفعة.
- تحديث لون المشترك تلقائياً بعد الدفع (`Payment.save()` → `subscriber.update_color_status()`).
- إنشاء سجل اشتراك تلقائي (`SubscriptionLog`) عند الدفع مع تمديد تاريخ الاشتراك.
- تسليم العهدة النقدية: المندوب يجمع العمليات المعلقة ويسلمها للمحاسب عبر `CollectionSettlement`.
- المحاسب يوافق/يرفض محضر التسليم — عند الموافقة تتحول حالة الدفعات المرتبطة.
- تسجيل المصروفات التشغيلية (وقود، صيانة، رواتب، تسويق، أخرى).
- تسجيل الجزاءات المالية للموظفين.
- إدارة السلف والمديونيات.
- مكافآت الموظفين.

حالات الدفعة (`Payment.Status`):

- `pending`: قيد الإيداع — المندوب حصّل ولم يسلم بعد.
- `deposited`: تم الإيداع — المندوب سلّم للمحاسب.
- `confirmed`: مؤكدة — المحاسب وافق.

مخطط لها (لم يُنفذ بعد):

- توثيق أعذار المتأخرين كجدول مستقل (`LatePaymentExcuse`) بدلاً من حقل `excuse` في `Subscriber` (FIN-07).

ملاحظة: تكلفة التحفيز البيئي (FIN-04) متضمنة في جدول `Reward` ولا تحتاج جدول مستقل.

المتطلبات: FIN-01 إلى FIN-07.

### وحدة التقارير (`reports`)

لا يحتاج جداول مستقلة — يعتمد على تجميع بيانات الجداول الأخرى.

المسؤوليات:

- لوحة المؤشرات: مناطق نشطة، مشتركين، موظفين، شكاوى، إيرادات، مصروفات، صافي الربح، توزيع الألوان.
- التقارير المالية: إيرادات شهرية، مصروفات شهرية، عدد المدينين.
- التقارير التشغيلية: نسبة الإنجاز اليومي، إحصائيات المناطق.
- تقارير النمو: مشتركين جدد شهرياً مع الإجمالي التراكمي.
- التصدير: PDF, Excel (xlsx), CSV.

المتطلبات: REP-01 إلى REP-05.

## تدفقات رئيسية

### تسجيل مشترك جديد (ميداني بواسطة المندوب)

1. المندوب يفتح شاشة `register.jsx`.
2. التطبيق يحاول التقاط إحداثيات GPS.
3. المندوب يدخل بيانات المشترك (الاسم، الهاتف، العنوان).
4. المندوب يختار باقة اشتراك (محملة ديناميكياً من `/api/plans/`).
5. **GPS Fallback**: إذا لم يُلتقط الموقع، يُربط المشترك بمنطقة المندوب (`profile_zone`).
6. Backend يُنشئ `User` + `Subscriber` + يولّد `subscription_id` فريد.
7. يتم استدعاء `update_color_status()` → المشترك يظهر بالأحمر (مستحق الدفع).

### التحصيل النقدي الميداني

1. المندوب يفتح شاشة `collect.jsx`.
2. يبحث عن المشترك بالاسم أو الهاتف أو الرقم (بحث ذكي مع قائمة منسدلة).
3. عند اختيار المشترك، يتعبأ حقل المبلغ بالرصيد المستحق تلقائياً.
4. المندوب يؤكد الدفع → Backend ينشئ `Payment` + يولّد `receipt_number`.
5. `Payment.save()` يستدعي `subscriber.update_color_status()` تلقائياً.
6. يتم إنشاء `SubscriptionLog` مع تمديد `subscription_end`.
7. تظهر الدفعة في السجل بحالة "قيد الإيداع".

### تسليم العهدة النقدية

1. بنر تنبيهي يظهر أعلى شاشة التحصيل عند وجود مبالغ معلقة.
2. المندوب ينقر "تسليم للمحاسب" → يتم إنشاء `CollectionSettlement` بحالة `pending`.
3. جميع الدفعات المعلقة ترتبط بمحضر التسليم (`Payment.settlement`).
4. حالة الدفعات تتحول إلى `deposited`.
5. المحاسب يرى محضر التسليم في `Settlements.jsx` → يوافق أو يرفض.
6. عند الموافقة: حالة المحضر تصبح `approved`.

### إعادة التدوير

1. المشترك يطلع على فئات الفرز في `education.jsx`.
2. يفتح `recycling.jsx` → يحدد الفئة وعدد الأكياس → يرسل الطلب.
3. السائق يرى الطلب ضمن دورة اليوم → يؤكد الاستلام.
4. النظام يمنح نقاط تلقائياً (`PointsTransaction`).
5. النقاط تظهر في لوحة المتصدرين.

## التكامل بين المكونات

- Mobile يتصل بالـ Backend عبر HTTP + JWT لتنفيذ وظائف المشترك والسائق والمندوب.
- Dashboard يتصل بالـ Backend عبر HTTP + JWT لتنفيذ وظائف الإدارة والمحاسبة.
- Backend هو المصدر المركزي لقواعد العمل — لا يتم حفظ business logic في الـ Frontend.
- MySQL هي مصدر البيانات الدائم.
- الإشعارات تُنشأ تلقائياً عند أحداث محددة في Backend.
- الخرائط تستخدم بيانات المناطق والمشتركين والشاحنات المخزنة في Backend.

## حدود المعمارية

- لا يتم إضافة متجر إلكتروني أو دفع إلكتروني — التحصيل نقدي فقط مع إيصال رقمي.
- لا يتم إضافة نظام صلاحيات تفصيلي — الفصل عبر واجهات مستقلة.
- لا يتم إضافة وظائف خارج نطاق الأدوار الخمسة المعتمدة.
- الأدمن (Admin) هو نفسه المدير — لا يوجد دور "Manager" منفصل.
