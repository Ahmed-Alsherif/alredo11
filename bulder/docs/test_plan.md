## 2. سيناريوهات الاختبار الموسعة (للتنفيذ)

### المصادقة والصلاحيات (Auth & RBAC)

| السيناريو | النتيجة المتوقعة |
|---|---|
| كل دور (admin/accountant/driver/agent/subscriber) يدخل لوحته | يرى فقط الشاشات والبيانات المسموح بها لدوره |
| محاولة وصول سائق لصفحة المالية | رفض (403 Forbidden) |
| محاولة وصول مشترك لقائمة الموظفين | رفض (403 Forbidden) |
| تسجيل دخول بكلمة مرور خاطئة | فشل (401 Unauthorized) |
| تغيير كلمة المرور بكلمة قديمة صحيحة | نجاح |
| إعادة تعيين كلمة المرور من المدير | نجاح |

### المشتركون

| السيناريو | النتيجة المتوقعة |
|---|---|
| تسجيل مشترك داخل حدود منطقة | نجاح + تحديد المنطقة تلقائياً + `color_status = 'red'` |
| تسجيل مشترك خارج حدود التغطية | فشل مع رسالة خطأ |
| تسجيل مشترك بدون GPS | يُربط تلقائياً بمنطقة المندوب (`profile_zone`) |
| `subscription_id` مكرر قبل الـ migration | الـ Migration تُوحد القيم المكررة |
| إيقاف مؤقت ثم استئناف | `subscription_end` يُمدد بأيام الإيقاف |
| أرشفة مشترك | يختفي من القائمة الافتراضية ويظهر عند `?archived=true` |
| تغيير خطة الاشتراك | الباقة الجديدة تُعكس في بيانات المشترك |
| التصنيف اللوني بعد الدفع | يُحدث تلقائياً بناءً على `subscription_end` |
| تحميل الباقات ديناميكياً | شاشة التسجيل تجلب الباقات من `/plans/` وتعرضها في قائمة منسدلة |

### المالية

| السيناريو | النتيجة المتوقعة |
|---|---|
| المندوب يحصّل من مشترك | `Payment(status='pending')` + إيصال فريد + إشعار + تحديث `color_status` |
| المحاسب يحول الدفع لـ deposited | `status` يتغير إلى `deposited` |
| المندوب يسلم عُهدة | `CollectionSettlement(status='pending')` + ربط الفواتير |
| المحاسب يعتمد محضر العُهدة | `Settlement.status = 'approved'` + فواتير `deposited` |
| `receipt_number` مكرر قبل الـ migration | الـ Migration تُوحد القيم المكررة |
| تسجيل مصروف جديد | `Expense` يُنشأ بالتصنيف المحدد |
| تسجيل سلفة وإغلاقها | `Advance(status='active')` → `mark_paid` → `Advance(status='paid')` |
| مطابقة العُهد | تظهر مجاميع pending/deposited لكل مندوب |

### الشكاوى والتقييمات

| السيناريو | النتيجة المتوقعة |
|---|---|
| مشترك يرسل شكوى | `Complaint(status='new')` مربوطة تلقائياً بالمشترك |
| المدير يغير حالة الشكوى لـ resolved | `resolved_at` يُسجل تلقائياً |
| تقييم شهري مكرر لنفس المشترك/الشهر | رفض (unique_together) |
| سائق يرسل بلاغ ميداني | `FieldReport` + إشعار داخلي للإدارة |

### إعادة التدوير

| السيناريو | النتيجة المتوقعة |
|---|---|
| مشترك يطلب جمع تدوير | `RecycleRequest(status='pending')` |
| سائق يؤكد الاستلام | `status='collected'` + `PointsTransaction` مرة واحدة |
| تأكيد مكرر لنفس الطلب | لا تُضاف نقاط إضافية (Idempotent) |
| السحب البيئي | فائز + `Reward` + تمديد اشتراك + مصروف marketing |
| تصدير XLSX | Content-Type = XLSX والملف يفتح بنجاح |

### الاختبار اليدوي حسب الدور

| مدير (admin) | Dashboard, Zones, Routes, Staff, Subscribers, Complaints, Finance, Recycling, Tracking, Reports, Notifications |

| مشترك (subscriber) | التسجيل/الدخول، الاشتراك والباقة، الإيقاف/الاستئناف، الشكاوى، التقييم، التدوير، الإشعارات، تتبع الشاحنة |

## 4. فحوصات سلامة البيانات (Data Integrity)

| الفحص | الطريقة | الهدف |
|---|---|---|
| `User` للمصادقة فقط | لا يوجد اعتماد على `user.phone` أو `user.first_name` | فصل الهوية عن البيانات |
| حقول العرض من البروفايل | استخدام `user.display_name`, `profile_phone`, `profile_zone` | اتساق البيانات |
| استمرارية الزيارات | `daily_list` ينشئ `CollectionVisit` فعلية وليست مؤقتة | عدم فقدان البيانات |
| فرادة الإيصالات | كل `Payment.receipt_number` فريد وغير فارغ | سلامة مالية |
| فرادة رقم الاشتراك | كل `Subscriber.subscription_id` فريد وغير فارغ | سلامة بيانات |
| نقاط التدوير | `PointsTransaction.recycle_request` يمنع النقاط المكررة | عدالة النظام |
| التقارير من بيانات حقيقية | التقارير المالية والتشغيلية تقرأ من الجداول الفعلية | دقة التقارير |
